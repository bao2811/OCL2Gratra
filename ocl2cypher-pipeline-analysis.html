Phân tích Kiến trúc Pipeline OCL2Cypher

Pipeline OCL to Cypher được thiết kế theo kiến trúc trình biên dịch (compiler architecture) hiện đại. Thay vì dịch trực tiếp từ văn bản OCL sang Cypher (dễ sinh lỗi và khó bảo trì khi biểu thức phức tạp), hệ thống chia quá trình thành 6 bước tách biệt. Việc chia nhỏ này giúp hệ thống dễ dàng kiểm tra kiểu (type checking), tối ưu hóa câu truy vấn đồ thị (graph query optimization), và hỗ trợ các biểu thức lồng nhau sâu không giới hạn.

Luồng dữ liệu tổng quan (Data Flow):
  • 1. Parser (Phân tích cú pháp): OCL Text → AST (Cây Cú pháp Trừu tượng)
  • 2. Semantic Binder (Kiểm tra ngữ nghĩa): AST → Bound Tree (Cây đã gắn nhãn Kiểu dữ liệu từ UML)
  • 3. IR Builder (Xây dựng Trung gian): Bound Tree → IR (Đại diện Trung gian, tách bạch rõ ràng Thuộc tính và Liên kết đồ thị)
  • 4. IR Optimizer (Tối ưu hóa): IR → Optimized IR (Gập các vòng lặp truyền thống thành các phép kiểm tra Đồ thị siêu tốc)
  • 5. Cypher Planner (Lập kế hoạch): Optimized IR → Cypher Plan (Bản vẽ cấu trúc truy vấn: Dùng Subquery hay List Comprehension)
  • 6. Cypher Renderer (Sinh mã Cypher): Cypher Plan → Cypher String (Cấp phát tên biến an toàn và trộn ra chuỗi lệnh cuối cùng)

Phần 1: Vòng đời của một Invariant Cơ bản qua 6 bước

1.1. OCL Đầu vào

context Family inv HasChildren: self.children->notEmpty()

Ý nghĩa OCL: Với mọi Family, invariant đúng khi family đó có ít nhất 1 Person ở role children.

1.2. Bước 1: Parser và AST

OclDocumentParser.parse(...) gọi OCLLexer, OCLParser, và ASTVisitor để phân tích cú pháp chuỗi văn bản thành một cây phân cấp. Cấu trúc thiết kế của các Node AST trong hệ thống được định nghĩa như sau:

ASTNode (Node Gốc)
 ├── ASTFile (Đại diện cho toàn bộ document OCL)
 ├── ASTContext (Đại diện cho một khối context ... inv ...)
 └── ASTExpression (Lớp cha của mọi biểu thức)
      ├── ASTVar (Biến, ví dụ: self, e)
      ├── ASTProperty (Truy cập thuộc tính hoặc liên kết, ví dụ: self.children)
      ├── ASTIterator (Vòng lặp, ví dụ: ->exists(e | ...), ->forAll)
      ├── ASTCollectionOp (Toán tử tập hợp không có thân, ví dụ: ->notEmpty(), ->size())
      ├── ASTMethodCall (Gọi hàm, ví dụ: .substring())
      ├── ASTBinary (Phép toán 2 ngôi, ví dụ: +, -, >, and, or, implies)
      ├── ASTNot (Phủ định)
      ├── ASTIf (Khối lệnh if/then/else/endif)
      ├── ASTLet (Khai báo biến cục bộ: let ... in ...)
      └── ASTLiteral (Hằng số: ASTIntegerLiteral, ASTStringLiteral, ASTBooleanLiteral, ...)

Áp dụng vào ví dụ cụ thể, AST rút gọn thu được về mặt ý nghĩa sẽ là:

ASTFile
└── ASTContext
    ├── className = "Family"
    ├── invName   = "HasChildren"
    └── expression =
        ASTCollectionOp
        ├── source =
        │   ASTProperty
        │   ├── source = ASTVar("self")
        │   └── name   = "children"
        ├── opName = "notEmpty"
        └── args   = []

Giải thích: Hệ thống mới biết cú pháp. Chưa biết children là attribute hay association, self kiểu gì, hay notEmpty() áp dụng lên cái gì.

1.3. Bước 2: Rule Extraction

OclRuleExtractor.extractRules(ASTFile) tạo ra một OclRuleDescriptor:

ownerKind = CLASS
ruleKind  = INV
className = "Family"
ruleName  = "HasChildren"
ast       = ASTContext(...)

Giải thích: Tầng này chỉ tách document thành đơn vị compile. Chưa semantic hóa biểu thức.

1.4. Bước 3: Semantic Binding

DefaultOclToCypherCompiler.compileContext(...) gọi metamodelIndex.requireClass("Family") và binder.bindContext(context). Cấu trúc thiết kế của các Node đã được gắn kết (Bound Tree) như sau:

BoundExpression (Lớp cha của biểu thức đã kiểm tra ngữ nghĩa)
 ├── BoundVariable (Biến đã gắn kiểu, ví dụ: e mang kiểu Node(Employee))
 ├── BoundProperty (Thuộc tính hoặc Navigation đã gắn siêu dữ liệu UML)
 ├── BoundIterator (Vòng lặp đã phân giải kiểu trả về)
 ├── BoundCollectionOperation (Toán tử tập hợp đã phân giải kiểu)
 ├── BoundBinary, BoundNot, BoundIf, BoundLet, BoundMethodCall...
 └── BoundLiteral

Bound tree ý nghĩa thu được cho ví dụ trên:

BoundContextInvariant
├── ast = ASTContext("Family", "HasChildren", ...)
└── expression =
    BoundCollectionOperation
    ├── source =
    │   BoundProperty
    │   ├── source =
    │   │   BoundVariable
    │   │   ├── ast  = ASTVar("self")
    │   │   └── type = NODE(Family)
    │   ├── attribute  = null
    │   ├── navigation = NavigationInfo(
    │   │   roleName           = "children",
    │   │   associationName    = "FamilyChildren",
    │   │   sourceClassName    = "Family",
    │   │   targetClassName    = "Person",
    │   │   resultBinding      = NODE_COLLECTION(Person, SET),
    │   │   sourceRoleName()   = "family",
    │   │   targetRoleName()   = "children",
    │   │   direction          = OUTGOING
    │   │ )
    │   └── type = NODE_COLLECTION(Person, ...)
    ├── operation = "notEmpty"
    ├── arguments = []
    └── type      = SCALAR(Boolean)

Giải thích bản chất: self đã là node Family. children đã thành navigation có metadata đầy đủ. Đây là bước quan trọng nhất về nghĩa.

1.5. Bước 4: Lowering sang IR

OclIrBuilder.buildInvariant(...) loại bỏ hoàn toàn dấu vết của AST và chuyển sang cấu trúc Trung gian (IR). Hệ thống định nghĩa cây IR như sau:

OclIr.Expression (Biểu thức Trung gian đồ thị)
 ├── Variable (Biến)
 ├── AttributeAccess (Truy cập thuộc tính dữ liệu trên một Node)
 ├── NavigationAccess (Bước nhảy qua cạnh đồ thị tới Node khác)
 ├── IteratorOperation (Vòng lặp chưa tối ưu)
 ├── CollectionOperation (Toán tử tập hợp chưa tối ưu)
 └── Binary, Not, If, Let, Literal, MethodCall...

Cây IR tạo ra cho ví dụ trên:

InvariantQuery
├── contextClassName = "Family"
├── invariantName    = "HasChildren"
└── predicate =
    CollectionOperation
    ├── source =
    │   NavigationAccess
    │   ├── source = Variable("self", NODE(Family))
    │   ├── navigation = NavigationInfo(FamilyChildren, family -> children, target = Person)
    │   └── type = NODE_COLLECTION(Person, ...)
    ├── operationName = "notEmpty"
    ├── arguments     = []
    └── type          = SCALAR(Boolean)

Giải thích: IR bỏ AST node cụ thể. BoundProperty đổi thành NavigationAccess.

1.6. Bước 5: IR Optimization

OclIrOptimizer.optimizeInvariant(...) duyệt cây IR từ dưới lên để gập (fold) các mẫu cồng kềnh thành các Node tối ưu đồ thị (Graph-optimized Nodes):

OclIr.Expression (Các Node bổ sung từ Optimizer)
 ├── NavigationPredicateCheck (Gập vòng lặp exists/forAll trên một Navigation thành truy vấn đường đi)
 └── NavigationCountComparison (Gập size() > 0 trên một Navigation thành đếm đường đi)

Mô hình sau khi rewrite lại:

InvariantQuery
├── contextClassName = "Family"
├── invariantName    = "HasChildren"
└── predicate =
    NavigationPredicateCheck
    ├── navigation   = NavigationAccess(self.children)
    ├── iteratorName = "nav"
    ├── predicate    = null
    ├── kind         = EXISTS
    └── type         = SCALAR(Boolean)

Giải thích rất quan trọng: Trước tối ưu: "lấy danh sách children rồi kiểm tra notEmpty". Sau tối ưu: "kiểm tra có tồn tại ít nhất một cạnh navigation không". Lợi ích: Backend sinh EXISTS { MATCH ... } cực kỳ tối ưu cho Đồ thị.

1.7. Bước 6: Planning sang Backend Plan

OclCypherPlanner.planInvariant(...) biến optimized IR thành các khối kế hoạch thi công sát với cú pháp Cypher:

OclCypherPlan.ExpressionPlan
 ├── VariablePlan (Đại diện cho biến trong Cypher)
 ├── NavigationMatchPlan (Mẫu MATCH trong Cypher: (a)-[r]->(b))
 ├── ExistsSubqueryPlan (Mệnh đề EXISTS { MATCH ... })
 ├── NotExistsSubqueryPlan (Mệnh đề NOT EXISTS { MATCH ... })
 ├── ComprehensionPlan (Cú pháp List Comprehension: [x IN list WHERE ... | x])
 └── ReducePlan, CasePlan, BinaryPlan, LiteralPlan...

Kế hoạch sinh ra cho ví dụ trên:

InvariantPlan
├── contextClassName = "Family"
├── invariantName    = "HasChildren"
└── predicate =
    ExistsSubqueryPlan
    └── match =
        NavigationMatchPlan
        ├── owner       = VariablePlan("self", NODE(Family))
        ├── targetAlias = "nav"
        ├── navigation  = NavigationAccessPlan(self.children)
        ├── predicate   = null
        ├── predicateMode = NONE
        └── targetType  = NODE(Person)

1.8. Bước 7: Render Cypher Cuối cùng

OclCypherRenderer.renderInvariant(...) sinh Cypher dạng thực tế:

MATCH (self)-[:ObjectInstanceOf]->(cls {name: $p1})
WHERE NOT coalesce(
  EXISTS {
    MATCH (self)-[r]->(nav)
    WHERE type(r) STARTS WITH 'Link'
      AND r.name = $p2
      AND r.sourceRole = $p3
      AND r.targetRole = $p4
  },
  false
)
RETURN self.use_id AS useId

Giải thích chính xác: Điểm hay dễ nhầm lẫn là Cypher sinh ra không trả về các object thỏa mãn invariant. Nó trả về các object vi phạm (sử dụng WHERE NOT). Invariant này sẽ trả về các Family không có children.

Tóm tắt biến đổi của cùng một ý nghĩa: 
OCL:         self.children->notEmpty()
AST:         CollectionOp(Property(Var("self"), "children"), "notEmpty")
Bound:       BoundCollectionOperation(source = BoundProperty(navigation), op = notEmpty)
IR:          CollectionOperation(source = NavigationAccess(self.children), op = notEmpty)
Opt IR:      NavigationPredicateCheck(navigation = self.children, kind = EXISTS)
Plan:        ExistsSubqueryPlan(NavigationMatchPlan(self -[FamilyChildren]-> nav))
Cypher:      EXISTS { MATCH (self)-[r]->(nav) WHERE ... }

Phần 2: Phân tích các mô hình tối ưu nâng cao (Advanced Optimizations)

Ví dụ 2.1: Tối ưu biến cục bộ (Let Expression)

let threshold = 18 in self.age >= threshold
  • IR Builder: Tạo ra Let(biến: "threshold", giá_trị: 18, thân: self.age >= threshold).
  • Optimizer: Nhận thấy threshold chỉ là một hằng số đơn giản (Literal), nó thực hiện Inlining (Thay thế trực tiếp). Nó biến mất khỏi cây IR và thân trở thành: self.age >= 18.
  • Kết quả Cypher: Hoàn toàn không còn dấu vết của lệnh Let hay hàm reduce phức tạp, Cypher chỉ đơn giản là: WHERE self.age >= 18.

Ví dụ 2.2: Lặp với điều kiện (Iterator Predicate)

self.children->exists(c | c.age >= 18)
  • IR Builder: Tạo IteratorOperation(op: exists, nguồn: NavigationAccess(children), thân: c.age >= 18).
  • Optimizer: Nhận diện mẫu vòng lặp trên Navigation đồ thị. Gập lại thành NavigationPredicateCheck(EXISTS) kèm theo predicate = c.age >= 18.
  • Kết quả Cypher: Chuyển thành một Subquery duy nhất thay vì lọc danh sách:
    EXISTS { MATCH (self)-[r]->(c:Person) WHERE c.age >= 18 }.

Ví dụ 2.3: Tối ưu chuỗi lồng nhau (Chain Optimization)

self.children->select(c | c.age >= 18)->notEmpty()
  • IR Builder: Tạo CollectionOperation(op: notEmpty, nguồn: IteratorOperation(op: select, thân: c.age >= 18)).
  • Optimizer: Phân tích từ dưới lên:
    • Thấy select() -> notEmpty(), thực chất ý nghĩa toán học chính là exists().
    • Rewrite IR thành: IteratorOperation(op: exists, thân: c.age >= 18).
    • Tiếp tục thấy exists nằm trên NavigationAccess, lại gập tiếp thành NavigationPredicateCheck(EXISTS).
  • Kết quả Cypher: Bất ngờ là câu lệnh OCL dài dòng ở trên sẽ sinh ra mã Cypher tối ưu y hệt như Ví dụ 2.2:
    EXISTS { MATCH (self)-[r]->(c:Person) WHERE c.age >= 18 }. Quá trình vật chất hóa danh sách (materialize list) bằng select hoàn toàn bị loại bỏ.

Ví dụ 2.4: Navigation lồng nhau (Nested Navigation / Chaining)

self.department.employee->notEmpty()
  • Binder & IR Builder: Do bản chất đệ quy, phép truy xuất liên tiếp được biểu diễn bằng các node bọc nhau (wrapping). Cây IR sẽ là: NavigationAccess(liên kết: employee, nguồn: NavigationAccess(liên kết: department, nguồn: Variable(self))).
  • Optimizer: Khi xử lý notEmpty(), bộ tối ưu sẽ nhận diện NavigationAccess(employee) ở ngoài cùng và gập lại thành NavigationPredicateCheck(EXISTS, employee). Nguồn của node này chính là NavigationAccess(department).
  • Kết quả Cypher: Renderer duyệt đệ quy và sẽ sinh ra biến trung gian an toàn. Lệnh Cypher thu được bảo toàn chính xác cấu trúc nhảy bậc:
    EXISTS { MATCH (self)-[:CompanyDept]->(var1)-[:DeptEmployee]->(e) }. Không có giới hạn về độ sâu của navigation.

Ví dụ 2.5: Vòng lặp lồng nhau (Nested Iterators & Scoping)

self.department->forAll(d | d.employee->exists(e | e.age > 18))
  • Semantic Binder: Quản lý Scope bằng ngăn xếp (Stack). Khi vào forAll, push d. Khi vào exists, push e. Lúc này trong hàm thân, hệ thống tra cứu được cả self, d, và e. Khi thoát vòng lặp, pop biến tương ứng.
  • IR Optimizer: Tối ưu hóa đệ quy từ dưới lên. Hàm exists bên trong biến thành NavigationPredicateCheck(EXISTS). Sau đó, hàm forAll bên ngoài tiếp tục gập thành NavigationPredicateCheck(FORALL). Cây IR lồng nhau:
    NavigationPredicateCheck(FORALL, d, thân: NavigationPredicateCheck(EXISTS, e, thân: e.age > 18)).
  • Kết quả Cypher: Biến forAll thành NOT EXISTS { ... NOT ( ... ) } lồng với EXISTS: 
    NOT EXISTS { 
  MATCH (self)-[r1]->(d:Department) 
  WHERE NOT (
    EXISTS { 
      MATCH (d)-[r2]->(e:Employee) 
      WHERE e.age > 18 
    }
  ) 
}
